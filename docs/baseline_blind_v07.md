# Lotto7x7 v0.7 — Matched Baselines, Rolling Origin, and Shadow Ledger

## Research question

Does a historical **image-derived candidate pool** contribute information beyond
random candidate generation and mathematical ticket-overlap control?

The unit being compared is **one portfolio of N=1..5 tickets per next draw**.
The shape-pool size M (default 100) is only a *research search space*; it is
not a purchased-ticket count. Each ticket has six main numbers, from 1..49.
The special number, official prize rules, and actual money stakes are excluded.

## Four arms, with fixed N and identical target draws

| Arm | Pool source | Selection | Purpose |
| --- | --- | --- | --- |
| B0 | Entire 6/49 universe | N unique random combinations | No-image, no-search reference |
| B1 | M unique uniform random combinations | Random, Shape-Diverse, Coverage-Optimized | Controls for the 100-candidate search stage |
| S1 | M distinct placements from historically observed image families | The same three selectors and N as B1 | Tests whether *shape-first pool generation* adds anything |
| B2 | Entire 6/49 universe | N disjoint six-number sets constructed from a permutation of 49 labels | Strong, non-image, overlap-controlled benchmark |

B2 is a **disjointness reference**, not an assertion of a globally optimal
portfolio for every threshold and parameter. Coverage-Optimized is the existing
v0.6 exact fair-probability greedy plus one-swap search. Both B1 and S1 reuse
that selector unchanged. Random numbers are generated by NumPy's seeded RNG;
all configuration, dataset digests, generated portfolios, and results are
recorded. `random` selection is uniform without replacement *within its own
candidate pool*. Every arm has the same **N**, even though B0 and B2 do not
construct an M-candidate search pool.

**Independently drawn fair 6/49 null:** for any N distinct fixed tickets,
P(max hits = 6) = N / 13,983,816. The exact >=3/4/5 probability can differ
with ticket overlaps. These exact fair probability differences are **not**
evidence that a ticket generator predicts a future draw.

## Rolling-origin backtest (exploratory)

For a target chronological index `t`, only the image sequence and draw IDs
`[0,t)` are passed to pool generators and ticket selectors. The cutoff is
`draw_id[t-1]`. The actual six winning main numbers for `t` are extracted **after**
the entire portfolio structure has been constructed. A separate record contains
cutoff hash, target ID, eight selected portfolios, and per-ticket realized hits.

- Default `--warmup 200`; the last `--eval-draws 12` eligible targets are
  evaluated at `--stride 1`. The default window is deliberately small for a
  command-line functional check, **not** for inference or statistical power.
- `B0/random`, `B1/random|shape-diverse|coverage-optimized`,
  `S1/random|shape-diverse|coverage-optimized`, `B2/disjoint` are the eight
  matched portfolio configurations.
- Output includes max-hit distributions 0..6, empirical >=3/4/5/6 frequencies,
  mean exact theoretical >=3, and exploratory 1000-replicate paired bootstrap
  difference intervals versus B0 on the same draw IDs.
- Bootstrap intervals are **unadjusted for multiple testing**. Adjacent rolling
  windows share historical training observations, and only a small number of
  held-out outcomes may be present. Do **not** treat an unadjusted interval as
  proof of significance; fix comparisons in advance and accumulate blind data.
- Historical 2,183 observations and prior 7x7 mapping analyses have been
  inspected. This entire replay is **retrospective/exploratory**, even though
  code enforces chronological cutoffs. Re-running after seeing its results
  and changing policies introduces researcher degrees of freedom.

### Windows / PowerShell

```powershell
cd D:\my-github\lotto649
$py = '.\.venv\Scripts\python.exe'
git pull --ff-only origin main
& $py -m unittest discover -s tests -v

# Functional retrospective evaluation; full B1/S1 optimizer is CPU-intensive.
& $py -m lotto7x7 baseline-study `
    --warmup 200 --eval-draws 12 --stride 1 `
    --size 100 --families 20 --count 5 --seed 649 `
    --out results/baseline_study_v07.json
```

Changing `--count` to 1..5 holds N constant across B0/B1/S1/B2 in that run.
For controlled comparison across N, fix the same draw IDs and RNG seed; use
separate versioned output files. No real tickets are purchased by the CLI.

## Prospective-ready shadow record

Create a new **exclusive** JSON file containing the four pre-draw arms, all
selected six-number tickets, the full candidate number pools for B1 and S1,
exact coverage, historical cutoff, input SHA256, code commit, seed, local UTC
creation time, and a SHA256 over canonical JSON fields excluding itself.

```powershell
# Run before a future draw. Specify a genuinely known latest cutoff.
& $py -m lotto7x7 shadow-snapshot `
    --cutoff-draw-id 115000101 `
    --size 100 --families 20 --count 5 --seed 649 `
    --out results/shadow_20261108_pre_draw.json

# Only AFTER an actual later draw, with its official six main numbers:
& $py -m lotto7x7 shadow-score `
    --snapshot results/shadow_20261108_pre_draw.json `
    --draw-id 115000102 --numbers '01,02,03,04,05,06' `
    --out results/shadow_20261108_post_draw.json
```

**The score command above uses a placeholder draw ID and placeholder winning
numbers**, not independently verified lottery results. Replace both only
after official results are released.
The recorded score draw ID must be strictly greater than the committed cutoff.
Both snapshot and score commands refuse to overwrite existing output files.
The post-draw scorer verifies the snapshot's SHA256 and the complete B0/B1/S1/B2
selected ticket contents and coverage. Snapshot generation takes no target-draw
number as input, and `--cutoff-draw-id` discards every later archive row.

**Critical distinction:** a local timestamp + hash **do not independently
prove a prediction existed before the draw**. For trustworthy prospective
validation, publish the snapshot hash and code commit to an externally
trusted, timestamped GitHub commit/issue (or another append-only ledger)
**before** the draw. Keep the original file, capture the exact draw ID and
official results later, and do not reselect after seeing them. This module
creates files locally; it does not independently publish a timestamped record.

## Mathematical and operational limitations

1. The 7x7 raster geometry is a visualization choice, not a model of lottery
   draw mechanics. Historical shape recurrence does not imply future signal.
2. B2 maximizes the *number of distinct covered labels* (6N), but is not
   marketed as universally optimal for all multivariate >=3/4/5 objectives.
3. B1 and S1 hold both M and N fixed when comparing their three selectors;
   B0/B2 hold N fixed but intentionally do not inherit M search bias.
4. The optimizer can improve **exact union coverage** for partial hits, not
   the immutable six-of-six probability under fair independent draws.
5. A retrospective win or several three-number hits can be chance; paired
   uncertainty, multiple comparisons, temporal dependence, and prospective
   outcomes matter much more than a single realized series.
6. The generated pool is not 100 purchased bets. Never sum alternative strategy
   portfolios into a fictitious 20- or 30-bet probability.
